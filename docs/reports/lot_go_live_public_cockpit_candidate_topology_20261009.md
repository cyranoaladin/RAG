# Lot go-live — topologie publique Cockpit/Redis candidate (9 octobre 2026)

## Périmètre et autorité

Base de travail fraîche après fusion de #308 : `origin/main=6441bf306bfd3b5b58ae7bbceff6119e48cdfd8a`, arbre `298545df8410a10376629cbc0920245ae3575be6`. Ce lot prépare **uniquement** la configuration et le préflight local du candidat blue-green. Aucun worker, staging ou service de production n'a été démarré. Aucun `compose up`, `--execute`, changement de vhost hôte ou écriture de données gouvernées n'entre dans ce lot.

Le Compose résolu attend exactement cinq services : `pgvector`, `ingestor`, `prometheus`, `cockpit` et `session-redis`. Seul `ingestor` joint `rag_net` et `bff_net`. Cockpit et Redis ne joignent que `bff_net`; pgvector et Prometheus ne joignent que `rag_net`. Les ports API, Prometheus et Cockpit sont publiés chacun une seule fois sur `127.0.0.1`, vers 8001, 9090 et 3000 respectivement, avec ports hôtes distincts. Ni pgvector ni Redis ne publient de port. Le volume Redis est nommé et isolé par projet/couleur ; les deux autres volumes historiques conservent leur isolement de projet.

L'image Cockpit est référencée par le dépôt fixe `ghcr.io/cyranoaladin/rag-cockpit@sha256:<digest requis>` et comparée à l'entrée `cockpit` de provenance **fournie au préflight**. Pour un Compose à cinq services, la voie live appelle le vérificateur canonique V2 ajouté par #308 ; l'ancien plan à trois services continue d'utiliser V1. Les tests de ce lot simulent la réponse du vérificateur et ne prouvent aucun run V2 live ou signature de readiness. L'image Redis est référencée par `docker.io/library/redis@sha256:<digest requis>` ; aucun digest final n'est défini ici. Aucun build depuis le checkout n'est permis dans le candidat. Le verdict du préflight reste `mutation_allowed=false`.

`cockpit.env` et `session-redis.acl` sont obligatoirement sous `NEXUS_RUNTIME_SECRETS_ROOT`, hors de tout checkout et du répertoire de matériaux scellés. Le premier est privé (`0600`), n'est pas embarqué dans l'image, et porte les paramètres de session/SSO/BFF. Le second est monté en lecture seule ; Redis utilise son ACL native avec un hash SHA-256 du mot de passe du client, la portée de clés `nexus:session:v1:*`, `GET`, `SET` et les commandes de connexion. Le préflight compare l'URL Redis interne, le hash ACL et les identités partagées Cockpit/API en mémoire, sans afficher de secret. Le fichier ACL réel doit être lisible par l'UID Redis de l'image finalement retenue ; cette compatibilité doit être vérifiée à la qualification finale. Les sessions sont persistées sur un volume propre à la couleur ; le passage à une autre couleur impose une nouvelle authentification des sessions non transférées.

Le vhost Cockpit candidat transmet seulement la page d'accueil, les ressources statiques Next.js, les routes Auth.js nécessaires à l'identification, `GET /api/collections` et `POST /api/search`. Il refuse les chemins chat, review, writer, ingestion, métriques et santé publics. Les en-têtes d'identité interne fournis par le navigateur sont retirés ; les en-têtes de proxy sont définis par Nginx. Le vhost API public existant conserve sa seule route `POST /search/v2`. Les deux templates restent inactifs sur l'hôte.

## Vérifications locales rejouées

Le 9 octobre 2026 à 17:26 UTC, dans un venv neuf de ce worktree, sans installation Python editable :

- `pytest` ciblé sur Compose, préflight, vhost Cockpit, provenance d'image #308 **et** suites historiques du plan signé/wrapper : 187 tests verts, dont une résolution Docker Compose réelle à cinq services passée dans le préflight, les variantes blue/green et les refus adverses (writer, réseau DB, port public, images non épinglées, secret absent/symlink/permissions, ACL divergente, port dupliqué, privilège et entrée de processus modifiés). Le plan signé existant à trois services reste plan-only ; la sélection du préflight à cinq services dépend de la présence d'une entrée `cockpit` dans la provenance fournie.
- Le test du workflow de provenance #308 : 8 tests et 11 subtests verts.
- `ruff 0.6.4 check` sur ces fichiers : vert, version verrouillée par `services/rag-engine/requirements.lock`.
- Témoin Nginx local avec certificat éphémère : les sept appels étudiants attendus atteignent le backend ; les routes interdites et les méthodes erronées ne l'atteignent pas. Ce témoin ne mesure ni la vraie application ni TLS/DNS externes.
- `NEXUS_REQUIRE_DOCKER=1 pytest test_public_bff_network_witness.py` : témoin Docker vert ; BFF joint les routes API prévues, pas la DB par DNS ni IP.
- Témoin Redis Docker local, sans port hôte, avec l'image upstream observée `redis:7.4.11-alpine` au digest d'index `sha256:858f009f9709ce576febc734aa78b8f6d624b82571f9ddb6bda4377c833b3499` : le client Node `redis` effectivement installé par `npm ci` effectue `SET NX`/`GET`; accès anonyme, mauvais mot de passe et clé hors préfixe sont refusés. Ce digest prouve seulement le témoin local ; il ne sélectionne ni ne signe l'image de release finale. Les conteneurs et réseaux éphémères ont été arrêtés et retirés.

La résolution réelle a révélé et corrigé un défaut préexistant du préflight : `docker compose config --format json` référence les volumes nommés par leurs **noms logiques** dans les services, tandis que l'objet `volumes` porte les noms physiques préfixés par projet. L'ancien contrôle comparait le service au nom physique et rejetait donc un candidat conforme. Le test d'intégration de résolution réelle empêche cette régression.
