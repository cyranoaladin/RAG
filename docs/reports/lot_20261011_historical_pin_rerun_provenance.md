# Lot — reçu historique du pin après un rerun de revue fiable

Base de travail : `origin/main=39bc7c32333b86d2a2fe236d29dd46d5e8962be8`, le 11 octobre 2026. La PR #334 est fusionnée par le commit `39bc7c32`, parent `61a6e82c`, avec le pin de la release 40b inchangé (SHA-256 `309144dc6de90dd8f6df9ceb45be754c259467d2055d93beada1bb8fbd45ab69`). Le contrôle de pin avant fusion avait réussi. Aucun transfert de texte, reçu post-fusion, écriture en base ou changement de service n'est produit par ce lot.

Le producteur `historical_staging_target_pin_receipt.py` refusait ensuite la fermeture malgré la review #334 `APPROVED` sur le HEAD `5c448099` et le statut `trusted-human-review/head-pinned=success` avant fusion. Diagnostic LIVE en lecture seule : le workflow `38166761769`, tentative 2, a été relancé avec l'événement `pull_request_target`, dont `head_sha` est le **HEAD de la PR**. Le producteur traitait toujours ce champ comme le SHA de la base, comportement valable seulement pour la voie `issue_comment`. La relecture de review fabriquait ainsi une base égale au HEAD et rendait `current_head_approval_missing`, puis le reçu était rejeté comme invalide. La tentative a commencé à `19:30:55 UTC`, le statut vert a été créé à `19:31:08 UTC`, et la fusion a eu lieu à `19:31:37 UTC`. Ces horaires désignent l'observation de #334, pas une autorisation réutilisable sans relecture.

Le correctif reconstruit la base historique depuis le **parent exact du squash merge**. Il conserve les deux événements du workflow de confiance : pour `issue_comment`, le run et sa tentative doivent porter cette base ; pour `pull_request_target`, ils doivent porter le HEAD approuvé de la PR. Les deux voies exigent toujours le même événement entre run et tentative, le run officiel, l'ID et la tentative liés au statut, la review exacte, l'ordre temporel pin → review → tentative → statut → fin → merge, le blob du pin inchangé, l'égalité des arbres du HEAD et du merge, et la cible live correspondante. Toute incohérence refuse le reçu.

Pour un rerun `pull_request_target`, l'API Actions de #334 retourne `pull_requests=[]` : ce champ vide ne lie donc pas le run à la PR. Le contrôle lie plutôt `run.head_branch` à `PR.head.ref`, les deux dépôts au dépôt attendu, et relit la liste officielle des PR sur cette branche et cette base, fermées incluses. À l'heure de début de la tentative, une seule PR doit être active sur la branche, avec le numéro et le HEAD revus ; une page pleine de 100 résultats, des métadonnées manquantes ou une ambiguïté sont refusées. Le chemin `issue_comment` conserve son contrôle historique et ne dépend pas de cette liste. Cette vérification répond au cas de deux PR sur des branches distinctes partageant le même commit, ainsi qu'au cas de plusieurs PR sur une même branche.

TDD : les tests ajoutés pour la voie `pull_request_target` ont d'abord échoué sur le code de `main` ; le test d'ambiguïté de PR a ensuite échoué avant son correctif. Après correction, **105 tests ciblés passent** (`test_historical_staging_target_pin_receipt.py`, `test_pr300_authority_receipt.py`, `test_independent_staging_target_pin.py`). Les sabotages couvrent événement inattendu ou discordant, mauvais HEAD ou base, mauvais run ou tentative, workflow étranger, chronologie fausse, branche ou dépôt divergent, PR voisine sur le même commit ou la même branche, candidat créé après ou fermé avant le run, HEAD du candidat différent et page de résultats incomplètement bornée. Le scénario positif couvre le `pull_requests=[]` réel ; le chemin `issue_comment` est testé séparément. Ruff ciblé sur les règles d'erreur Python (`E4,E7,E9,F`) et `git diff --check` passent. Le contrôle Ruff complet des deux fichiers remonte aussi des écarts de style déjà présents à la base ; aucun autre script n'a été reformatté.

La fusion de cette PR technique est nécessaire avant de rejouer le CLI canonique sur un checkout propre du `main` courant et la cible dédiée. Le reçu sera créé seulement après cette fusion et sa propre relecture GitHub/Git/DB ; le correctif de code seul n'autorise ni transfert V1/V2 ni publication.
