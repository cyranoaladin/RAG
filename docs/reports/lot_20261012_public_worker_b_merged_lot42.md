## Correction

Le chemin historique n'est activé que par le verdict C recomposé depuis la readiness signée : identité de la release, revue et digest du batch, base/HEAD/tree/review/challenge/reviewer exacts et instant de vérification C. La PR #338 doit être réellement fusionnée avant C. `verify_review` relit la PR, toutes les reviews, la permission du reviewer et le statut `trusted-human-review/head-pinned` sur le HEAD ; une review retirée, un HEAD divergent, une permission perdue, un statut rouge ou un transport indisponible refusent. Une PR fermée sans reçu C reste refusée. Le REST GitHub épinglé `2026-03-10` renvoie actuellement `merge_commit_sha=null` pour #338 : l'état `merged=true`, `merged_at` UTC antérieur à C et le reçu historique C contenant le SHA de merge ferment ce cas sans inventer un SHA live. Le statut requis est choisi par `created_at` puis `id`; un vieux succès ne masque plus un échec récent.

La preuve C est propagée dans les chemins de reprise, promotion, ancre LOT42 et publisher. Les contrôles de DB, de révocation, de validité, de contenu, de projection et de scope restent exécutés à chaque checkpoint. Un cache des seules réponses GitHub `GET 200` est borné à un job Worker B public, et ne s'active qu'après une première vérification LOT42 et LOT41A complète. Avant le dernier contrôle situé dans la transaction produit, après extraction/embedding et sous fence du plan de contrôle, le cache est vidé et désactivé : toutes les preuves externes sont relues live et un refus provoque le rollback produit. Aucun autre pipeline n'active ce cache.
