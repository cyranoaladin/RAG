## Contexte

`feat/rag-go-live-20260804` a développé, sur plusieurs lots (LOT44a à LOT44e), un pipeline d'ingestion agentique gouverné complet : contrats canoniques (`nexus_contracts.ingestion`, `resource_state`), plan de contrôle PostgreSQL (`ingestion_control`), huit stages déterministes (Scout → Fetcher → Extractor → Classifier → RightsAgent → QualityAgent, plus Planner/CoverageAgent), un scheduler/worker CLI, et un câblage best-effort de l'ancien endpoint `/ingest/v2` de `api.py`. Cette ligne de travail supposait implicitement que `api.py` (le monolithe historique, lecture + revue + écriture + administration) resterait le runtime de production.

Indépendamment et en parallèle, `origin/main` a fermé cette même surface par LOT41U/LOT41V (ADR-0024, ADR-0025) : le runtime de production devient `api_v2.py`, une application minimale lecture + revue **sans aucune route d'écriture**, construite par allowlist Docker explicite (aucun parseur de document, aucun client de source distante, aucun Celery, `ssrf_guard.py` absent). ADR-0024 énonce explicitement que toute écriture future nécessite une autorité externe non encore implémentée (« LOT41A », « LOT42 ») et interdit toute réactivation de l'ancien writer par variable d'environnement. ADR-0025 exige une review humaine formelle du Code Owner `@abenrhouma` sur le HEAD exact avant fusion.

Une inspection en lecture seule de la production Hetzner (`root@88.99.254.59`, `rag-ui.nexusreussite.academy` / `rag-api.nexusreussite.academy`) a confirmé que `api_v2:app` est le runtime réellement déployé — cohérent avec `origin/main`, pas avec `feat/rag-go-live-20260804`. Le propriétaire du dépôt a explicitement tranché ce conflit (décision de gouvernance verbale, consignée dans ce dépôt de travail, non reproduite ici in extenso) : `origin/main`, `api_v2:app`, ADR-0024 et ADR-0025 sont l'architecture et la gouvernance canoniques actuelles ; `feat/rag-go-live-20260804` n'est pas déployé tel quel ; le pipeline LOT44 doit être **réconcilié** sur la base d'`origin/main`, jamais fusionné aveuglément.

Ce document propose cette réconciliation.

## Décision 1 — Le worker d'ingestion gouvernée devient un composant isolé, jamais un correctif d'`api_v2.py`

Le pipeline LOT44 (`ingestion_control`, `ingestion_agents`, `ingestion_profiles`, `ingestion_worker`, `ssrf_guard.py`) est porté sur cette branche **sans modifier `api_v2.py`, `Dockerfile.ingestor-v2` ni les services `pgvector`/`ingestor`/`prometheus` de `docker-compose.v2.yml`**. `git diff origin/main -- services/rag-engine/infra/docker-compose.v2.yml` ne contient aucune ligne supprimée : toute addition de ce lot est strictement additive.

Le worker est construit par une image Docker séparée (`Dockerfile.ingestion-worker`), avec sa propre allowlist de fichiers COPY et son propre fichier de dépendances minimal (`requirements.ingestion-worker.txt`, audité contre les imports réels — ni FastAPI, ni Torch, ni modèle d'embedding : ce worker ne sert aucune route HTTP et ne fait aucun retrieval). Le service `ingestion-worker` ne déclare **aucun bloc `ports:`** — vérifié programmatiquement (`assert 'ports' not in doc['services']['ingestion-worker']`) et par `docker port` sur un conteneur réellement démarré, qui ne retourne rien. Aucune route publique, aucune interface réseau entrante : seul `docker exec` depuis l'hôte y donne accès.

La création de job — qui reposait dans le prototype initial sur l'endpoint `/ingest/v2` d'`api.py` — devient un outil opérateur en ligne de commande (`ingestion_worker/create_job_cli.py`), invoqué uniquement via `docker exec` par un opérateur humain authentifié sur l'hôte. `ingest_v2_bridge.py` (le pont HTTP du prototype initial) n'est **pas** porté sur cette branche : `api_v2.py` ne possède et ne doit posséder aucun endpoint d'écriture — en créer un recréerait exactement le writer public qu'ADR-0024 a fermé.

Le schéma `ingestion_control` reste, comme décidé dans le prototype initial (LOT44b, décision D1), un schéma logique séparé sur la **même** instance PostgreSQL que `pgvector` — aucun conteneur de base de données supplémentaire, aucun volume de données supplémentaire pour ce schéma. Son provisioning (migrations + rôles PostgreSQL dédiés `ingestion_control_migrator`/`ingestion_control_app`) est effectué par un service `migrator-ingestion-control` séparé, ponctuel (`restart: "no"`), qui se connecte au conteneur `pgvector` existant comme un client réseau ordinaire — jamais via les scripts `docker-entrypoint-initdb.d` du service `pgvector` lui-même, ce qui aurait exigé de modifier son bloc de service.

**Preuve technique** (rejouée sur une stack Docker isolée, réseau/volumes/conteneurs dédiés, jamais la production) : `pgvector` → `migrator-ingestion-control` (6 migrations appliquées, 2 rôles provisionnés, sortie 0) → `ingestion-worker` (démarre, heartbeat sain) → un job soumis via `create_job_cli.py` traverse réellement DISCOVERED → CANDIDATE → FETCHED → STORED → EXTRACTED → CLASSIFIED → RIGHTS_CHECKED → QUALITY_CHECKED, avec un `job_id` unique propagé à travers `workflow_events`, et un artefact réel récupéré depuis `https://example.com/` (559 octets, `text/html`) — preuve en conditions réelles que le correctif SSRF (Décision 2, ci-dessous) fonctionne dans le runtime construit, pas seulement en test unitaire isolé. Le gate de démarrage a également été prouvé fail-closed : un worker lancé sans profil/manifest valide refuse de démarrer (`WORKER_STARTUP_GATE_FAILED`, code de sortie 1).

## Décision 2 — Correctif LOT43 : double décompression dans `ssrf_guard.safe_fetch`

`safe_fetch` reconstruisait un `httpx.Response` à partir du corps déjà décodé par `iter_bytes()` (qui décode automatiquement gzip/deflate/br/zstd selon `Content-Encoding`), tout en conservant l'en-tête `Content-Encoding` d'origine sur la réponse reconstruite. Tout appelant lisant ensuite `.content`/`.text` déclenchait une seconde tentative de décompression sur des octets déjà en clair (`zlib.error: incorrect header check`), un bug systématique sur toute réponse HTTPS compressée (reproduit indépendamment du domaine : `example.com`, `eduscol.education.fr`).

**Correctif** : les en-têtes `content-encoding`/`content-length`/`transfer-encoding` — devenus caducs une fois le corps déjà décodé — sont retirés avant reconstruction de la réponse ; `httpx` recalcule un `Content-Length` exact sur le corps décodé. Toutes les protections SSRF existantes (revalidation DNS par saut, blocage IP privée/loopback/lien-local/metadata cloud, bornage de taille en streaming, limite de redirections) restent inchangées.

Couverture de test ajoutée (`tests/test_ssrf_guard.py`, 23 tests au total, 7 nouveaux) : gzip et deflate valides (roundtrip exact + absence de `content-encoding` résiduel), recalcul correct de `Content-Length`, corps compressé malformé (rejet explicite `httpx.DecodingError`, jamais un contenu corrompu silencieux), bombe de décompression (bornée par `max_bytes` sur la taille décodée, pas la taille sur le fil), décompression across une redirection, non-régression sur une réponse non compressée.

## Décision 3 — Couche d'autorité minimale (pas une implémentation de LOT41A/LOT42)

ADR-0024 identifie explicitement « l'autorité externe LOT41A » et « les attestations de publication LOT42 » comme prérequis, non implémentés, à toute réouverture d'un chemin d'écriture. `docs/ROADMAP.md` les référence de la même façon, comme travaux futurs. Une recherche explicite dans ce dépôt — code, ADRs, traces serveur — confirme qu'**aucune définition, aucun contrat, aucune implémentation partielle de LOT41A ni LOT42 n'existe à ce jour**.

Ce lot n'invente pas d'autorité de substitution. Il livre le strict minimum qui rend le gate LOT44c (`enforce_production_manifest_gate`) fail-closed sur l'**absence d'autorité**, pas seulement sur l'absence de fichier : chaque entrée de manifest (`ingestion_profiles/manifest.py`) doit désormais porter `approved_by` (identité humaine nommée, non vide) et `approved_at` (horodatage ISO 8601 valide), sous peine de rejet explicite (`ProfileManifestError`) — exactement au même niveau d'exigence que `fingerprint`. Ces deux champs font partie du contenu figé du manifest : falsifier l'un ou l'autre change l'empreinte SHA-256 du manifest entier (prouvé par test dédié). Le worker et l'outil de création de job consignent, à chaque démarrage/création, l'autorité et l'empreinte de manifest sous lesquelles ils opèrent (`WORKER_STARTUP_AUTHORITY`, `JOB_CREATION_AUTHORITY`), jamais silencieusement.

Cette couche **ne constitue pas** une autorisation de scope (LOT41A) ni une chaîne d'attestations quality→gate→review (LOT42) : elle ne fait que garantir qu'aucune entrée de manifest ne peut être acceptée sans une trace d'approbation humaine attribuable. Tant qu'aucun manifest réel, approuvé par une autorité humaine nommée réelle, n'existe dans ce dépôt — ce qui reste le cas aujourd'hui, aucun profil de production n'étant livré par ce lot ni les précédents — le gate continue d'échouer explicitement, et le worker ne peut pas démarrer en production. Ce lot ne crée, n'approuve ni ne place aucun profil ou manifest réel.

## Décision 4 — Renumérotation des ADR LOT44 (pas de conflit avec la numérotation acceptée)

`feat/rag-go-live-20260804` avait numéroté ses cinq ADR LOT44a-e ADR-0024 à ADR-0028, en collision directe avec ADR-0024 (Accepté, runtime v2) et ADR-0025 (Accepté, autorité de revue) déjà acceptés sur `origin/main`. Ces cinq documents sont renumérotés ADR-0026 à ADR-0030 (mapping `0024→0026, 0025→0027, 0026→0028, 0027→0029, 0028→0030`, appliqué en une seule passe programmatique pour éviter toute double-substitution en cascade), et chaque référence croisée dans leur propre contenu ainsi que dans les docstrings/commentaires du code source LOT44 porté sur cette branche est mise à jour en conséquence. Le contenu technique de ces cinq documents n'est pas modifié au fond — seule leur numérotation change. Cet ADR-0031 est le premier numéro réellement libre après cette renumérotation.

## Relation à ADR-0024 et ADR-0025 — non-supersession explicite

Ce document ne déclare ADR-0024 ni ADR-0025 supersédés, affaiblis ou rouverts. `api_v2:app` reste l'unique point d'entrée du runtime de production. Aucune route d'écriture n'est ajoutée à `api_v2.py`. Le worker ne contourne jamais la gouvernance d'`api_v2.py` — il ne l'appelle jamais, ne partage aucun processus avec lui, et n'est joignable par aucun chemin réseau qu'`api_v2.py` emprunterait. Le principe fail-closed d'ADR-0024 (aucune activation par défaut, aucun bypass par variable d'environnement) et l'exigence de review humaine sur le HEAD exact d'ADR-0025 sont repris à l'identique pour ce lot : voir le champ **Statut**, ci-dessus.

## Décision 5 — Remédiation de la revue PR#90 (Codex, Cubic, GitGuardian)

Après ouverture de la PR#90 sur le HEAD initial `9306f1cb4f92037c09a2edb63b78665be0afcc79`, les revues automatisées Codex et Cubic ont fait remonter 45 signalements (5 + 40) et GitGuardian 5 occurrences d'un même incident. Le propriétaire du dépôt a explicitement refusé d'approuver ce HEAD et mandaté leur traitement complet, signalement par signalement, avant toute nouvelle demande d'approbation — cf. `docs/reports/pr90_review_remediation_matrix.md` pour la matrice complète (diagnostic, décision, correction, test, par signalement).

Points structurants de cette remédiation, qui **modifient** les décisions ci-dessus (1 à 4) sans les contredire dans leur principe :

- **Décision 1 amendée** : le plan de contrôle d'ingestion (``migrator-ingestion-control``/``ingestion-worker``) ne vit plus dans `docker-compose.v2.yml` mais dans un fichier séparé, strictement opt-in, `docker-compose.ingestion.yml` — `docker-compose.v2.yml` est revenu à l'état exact d'`origin/main` (`git diff origin/main` : zéro ligne modifiée). Le principe d'isolation de la Décision 1 est renforcé, pas affaibli : le runtime v2 normal ne référence même plus l'existence de ce plan de contrôle.
- **Le worker garde en mémoire, pour toute sa durée de vie, l'exact `ProfileRegistry` vérifié au démarrage** (`WorkerDeps.profile_registry`) — plus aucun rechargement depuis le disque à chaque job, fermant une fenêtre où un profil modifié sur l'hôte après démarrage aurait pu être utilisé sans revérification contre le manifest approuvé.
- **`niveau_conformity`/`voie_conformity`/`programme_conformity` (Classifier, LOT44d) valent désormais `False`** ("non vérifié") au lieu de `True` codé en dur, et `QualityAgent` les traite comme des motifs de rejet explicites — **`QUALITY_CHECKED -> ROUTED` devient structurellement inatteignable** tant qu'aucun classifieur réel ne remplace ce placeholder. C'est un changement de comportement intentionnel, pas une régression : LOT44d n'a jamais prouvé ces trois dimensions à partir du contenu, seule leur valeur affichée changeait.
- **Identité canonique de dédoublonnage unifiée** : le `dedup_key` par défaut de l'outil opérateur (`create_job_cli.py`) est désormais dérivé de `canonical_url` (même identité que Scout), et la création de job passe par une nouvelle primitive atomique (`find_or_create_job`, verrou advisory PostgreSQL) — prouvée par un test de concurrence réel (deux connexions PostgreSQL distinctes, deux threads).
- **Toutes les primitives de bail** (`complete_job`, `record_job_retry`, `set_job_resource_id`, `record_retry`, `claim_resource`, `claim_job`) exigent désormais une expiration de bail strictement future, pas seulement un jeton correspondant — sémantique de bail stricte.
- **Correctif SSRF complémentaire** : RFC 6598 (`100.64.0.0/10`) désormais bloqué (`not ip.is_global`, combiné aux vérifications existantes, jamais à leur place — `is_global` vaut `True` pour une adresse multicast, vérifié empiriquement).
- **Provisioning PostgreSQL durci** : mots de passe transmis via `\getenv` (jamais visibles dans les arguments du processus `psql`, prouvé par inspection réelle de `ps`), collision `MIGRATOR_ROLE == APP_ROLE` rejetée, attributs de moindre privilège réalignés sur un rôle déjà présent.
- **Migrations/rollbacks rendus concurrency-safe et upgrade-safe** : `LOCK TABLE ... ACCESS EXCLUSIVE` avant chaque garde de vacuité de rollback (001-004), migration 005 réconcilie tout `status='claimed'` préexistant plutôt que d'échouer, migration 006 échoue explicitement (jamais un payload `{}` inutilisable) sur une table déjà peuplée, migration 004 idempotente sur rejeu (`ADD CONSTRAINT` gardé par vérification `pg_constraint`).

**Non corrigé à l'issue de cette passe** : `planner.py::plan_search_core` n'appliquait toujours pas `profile.max_queries_per_run` (Cubic C26, P2) — reporté hors périmètre. **Corrigé en Décision 6** (revue incrémentale, passe 2) : ce report a été jugé, sur reconsidération, insuffisamment justifié pour un correctif aussi isolable — voir ci-dessous.

Validation complète après remédiation : `ruff check .` et `mypy src` propres, suite unitaire complète verte, suite d'intégration complète verte (PostgreSQL réel, y compris un test de concurrence multi-connexions et un test d'inspection de processus réel) — détail exact dans le rapport de lot mis à jour.

## Décision 6 — Remédiation de la revue incrémentale PR#90 (passe 2, 28 nouveaux signalements Cubic)

Après la remédiation de la Décision 5, une revue Cubic incrémentale a publié 28 nouveaux problèmes (11 P1, 10 P2, 7 P3) sur le HEAD alors atteint. Le propriétaire du dépôt a explicitement constaté que ce HEAD n'était donc pas approuvé, malgré un rapport antérieur erroné le déclarant stable, et a mandaté une seconde passe complète — cf. `docs/reports/pr90_review_remediation_matrix.md`, section « Revue incrémentale — passe 2 », pour la matrice complète (diagnostic, décision, correction, test, par signalement, y compris les 9 items désignés explicitement par lettre A-I dans le mandat opérateur).

Points structurants de cette seconde passe, qui **modifient** les décisions ci-dessus sans les contredire dans leur principe :

- **Toutes les gardes de bail restantes utilisent désormais `clock_timestamp()`**, pas `now()` (`complete_job`, `record_job_retry`, `set_job_resource_id`, `record_retry`) — `now()` reste figé à l'heure de début de transaction PostgreSQL ; une transaction restée ouverte au-delà de l'expiration réelle du bail pouvait encore réussir une opération qu'elle n'aurait jamais dû pouvoir terminer. Chacun des quatre correctifs est prouvé par un test transactionnel réel (transaction commencée avant expiration, opération tentée après expiration réelle, dans la même transaction).
- **Runner officiel de rollback** (`infra/scripts/rollback_ingestion_control_schema.sh`) : remplace tout usage de `psql -f rollback.sql` fichier par fichier. Garantit, dans une seule transaction, la quiescence de l'ingestion (refuse si un job est `running` ou si une ressource porte un bail actif), un ordre de verrouillage canonique fixe des six tables du schéma, et un commit uniquement si toute la plage annulée réussit.
- **Migration 006 verrouille désormais `resource_candidates`/`artifacts` avant son préflight de vacuité**, pas seulement autour — fermant la même classe de fenêtre de course que les rollbacks 001-004 (Décision 5) mais pour une migration forward.
- **`make v2-ingestion-up` utilise désormais `--wait`** — l'ancienne cible annonçait un succès dès que les conteneurs étaient *créés*, indépendamment de l'issue réelle du migrateur ou de la santé du worker (prouvé vulnérable empiriquement : un scénario réel migrateur-réussi/worker-jamais-healthy retournait code 0 sans `--wait`).
- **Attestation de rôle obligatoire au démarrage du worker** (nouveau module `ingestion_control/attestation.py`) : `current_user` attendu, non-superutilisateur, sans `CREATEDB`/`CREATEROLE`/`REPLICATION`/`BYPASSRLS`, sans propriété du schéma `ingestion_control`, sans privilège excédentaire sur `workflow_events`, sans appartenance à un autre rôle (aucune voie de `SET ROLE` vers une autorité supérieure). Un DSN de superutilisateur est désormais explicitement refusé au démarrage — prouvé par test réel.
- **Provisioning des rôles PostgreSQL durci davantage** : rejet de `MIGRATOR_ROLE`/`APP_ROLE` égal à `PGUSER` (en plus de la collision entre eux, déjà rejetée en Décision 5), et révocation inconditionnelle de toute appartenance préexistante d'un rôle géré à un autre rôle (aucune appartenance n'est jamais accordée par ce script — toute appartenance trouvée est par construction non autorisée).
- **Identité d'idempotence job-level corrigée** : `(collection, dedup_key)`, jamais `dedup_key` seul — la même URL soumise pour deux collections distinctes est désormais traitée comme deux soumissions indépendantes, jamais un doublon silencieux. Une soumission réellement dupliquée ne laisse plus de ligne `ingestion_runs` orpheline (marquée `'cancelled'`, jamais supprimée : le rôle applicatif ne détient pas `DELETE` sur cette table).
- **TOCTOU de lecture d'artefact fermée** (`ingestion_worker/storage.py`) : ouverture atomique composant par composant (`O_NOFOLLOW`), remplace la paire `Path.resolve()`/`read_bytes()` — prouvée par un test de course réelle (deux threads, bascule symlink/fichier en boucle) qui interceptait effectivement un secret hors `base_dir` sur l'implémentation non corrigée.
- **`planner.py::plan_search_core` applique désormais `profile.max_queries_per_run`** — le report de la Décision 5 est reconsidéré : un profil gouverné porte ce budget explicitement, le laisser sans effet était jugé inacceptable pour une release gouvernée par le mandat opérateur de cette seconde passe. Correction isolée (troncature après déduplication et assemblage gap-targets-d'abord), 6 nouveaux tests.
- **Classification de retry HTTP corrigée** (`fetcher.py`) : dérivée de la plage de code HTTP (4xx vs 5xx, seul 429 excepté) plutôt que d'une énumération de codes non-réessayables à maintenir manuellement — l'ancienne liste classait par défaut réessayable tout code 4xx qu'elle omettait.
- **Normalisation de nom d'hôte cohérente** (`scout.py`) : `domain` déclaré et entrées `allowed_domains` du profil normalisés exactement comme les hôtes dérivés d'URL, jamais seulement ces derniers.
- **Politique explicite pour le YAML du manifest de production** (`manifest.py`) : clé non-hachable rejetée avec une erreur maîtrisée (au lieu d'un `TypeError` brut) ; ancres/alias/clés de fusion (`&`/`*`/`<<`) rejetés inconditionnellement — un manifest d'approbation nominative doit rester une déclaration littérale, auditable par simple lecture humaine.
- **Résolution de volume de sauvegarde corrigée** (`backup-volumes.sh`) : par étiquettes Compose (`com.docker.compose.project`+`com.docker.compose.volume`), jamais par nom nu supposé — un `docker compose up` sans `-p` explicite préfixe systématiquement les volumes du nom du projet, ce que le script précédent ignorait silencieusement.
- **Runbook opérationnel créé** (`docs/runbooks/ingestion_control_go_live.md`) : référencé depuis la Décision 5 mais jamais livré — couvre démarrage, création de job, rollback, attestation, sauvegarde/restauration, diagnostics.

**Discipline de vérification appliquée à cette passe** : chaque correctif a été vérifié individuellement en le faisant échouer sur une version temporairement non corrigée du code (revert ciblé du fichier concerné, exécution du test, restauration du correctif) avant d'être accepté comme preuve — pas seulement un test qui passe sur le code déjà corrigé. Plusieurs de ces vérifications ont révélé des détails d'implémentation non anticipés (ex. le rôle applicatif ne détient pas `DELETE` sur `ingestion_runs`, découvert en testant la primitive de nettoyage d'orphelin ; l'ordre `LOCK TABLE` avant `DO $nexus$` ne pouvait pas, seul, être distingué comportementalement d'un verrou implicite pris seulement à l'`ALTER TABLE`, nécessitant un test structurel complémentaire).

Validation complète après cette seconde passe : `ruff check src/ingestor/` propre, `mypy` propre sur les 11 fichiers source modifiés, suite unitaire complète verte (1730 tests), suite d'intégration complète verte (PostgreSQL/Docker réels, 117 passés, 9 ignorés sans rapport avec cette passe, 0 échec) — détail exact dans `docs/reports/pr90_review_remediation_matrix.md`.

**Statut de cet ADR à l'issue de cette seconde passe (constat historique, au moment de sa rédaction) : toujours Proposé, non Accepté.** Cette passe ne constituait ni une approbation, ni une demande d'approbation implicite — la review humaine `APPROVED` du Code Owner exigée par ADR-0025, sur le HEAD exact final de cette passe, restait entièrement à obtenir séparément. Aucune fusion, aucune écriture de production, aucune activation de gouvernance n'avait eu lieu ni n'était proposée par cette passe.

**Ce constat est désormais dépassé** : la review humaine `APPROVED` a depuis été obtenue sur le HEAD exact `36dca9285004d6efe886daf16bc11e5e0e3214cd` de la branche `reconcile/lot44-governed-ingestion-on-main`, et cet ADR est passé au statut **Accepté** — voir « Preuve d'acceptation », plus bas, et le champ **Statut** en tête de document.
